Reading the diagram

There is no code in this repo that calls an LLM. Stages 1 and 3 happen because a person — or Claude Code — hands a prompt template plus inputs to Claude. The teal box and the hierarchy dump feeding the top are the only executable pieces; everything neutral is a file on disk.

Generation is grounded: the flow may only use selectors that appear in a real view hierarchy dumped from the running app — without it, the model invents selectors. The flow YAML is committed and code-reviewed like a PR (runs/ is not committed); generated does not mean trusted. And the dashed loop is the part that compounds: each run teaches a selector or timing rule that gets written back into the prompt, so the next flow is sharper. The first story needed two fixes, the second a reliability fix, the third passed first try.

How a generated flow stays valid Maestro YAML

Honest answer: nothing in this repo validates the YAML before it runs — there is no Maestro schema or linter between Claude and the device. Instead, correctness is enforced by four layers, ordered by when each one catches a mistake.

  1. 1

    The prompt pins the convention prevention

    prompts/generate-flow.md embeds an explicit allow-list of Maestro commands and the required two-document shape (appId:, then ---, then steps), with a hard rule: don't use a command outside the list unless certain it exists. The convention lives in the prompt as source, not in the model's memory.

  2. 2

    Claude fills the gaps generation

    Within that subset the model supplies indentation, the map-vs-string forms, and selector regexes. Useful but fuzzy — trusted only because layers 3 and 4 follow it.

  3. 3

    A human reviews the flow review

    The flow is committed and read like a PR before it is trusted — which is exactly why apps/*/flows/ is in git and runs/ is not.

  4. 4

    Maestro is the real validator source of truth

    maestro test inside run_flow.sh parses the YAML and rejects malformed structure or unknown commands at runtime — the run just fails. There is no separate spec the model is checked against; the CLI's own parser is the spec. This is why the docs at docs.maestro.dev, not the model, are treated as authoritative.

The gap, and how to close it

A syntactically broken flow isn't caught until you spend ~15s running it on a device. The natural fix is a static pre-flight between stages 1 and 2 — parse the YAML and check commands against the same allow-list, no device needed. A first sketch:

# scripts/validate_flow.sh — static pre-flight before run_flow.sh (proposed)
set -euo pipefail
FLOW="${1:?usage: validate_flow.sh <flow.yaml>}"

# 1. must declare an appId and the --- document separator
grep -qE '^appId:[[:space:]]*\S' "$FLOW" || { echo "missing appId"; exit 1; }
grep -qxF '---' "$FLOW" || { echo "missing --- separator"; exit 1; }

# 2. every step command must be in the allow-list from the prompt
ALLOW='launchApp|tapOn|inputText|assertVisible|assertNotVisible|scroll'
ALLOW="$ALLOW|scrollUntilVisible|back|takeScreenshot|waitForAnimationToEnd"
ALLOW="$ALLOW|extendedWaitUntil|stopApp"
grep -oE '^[[:space:]]*-[[:space:]]+[a-zA-Z]+' "$FLOW" \
  | sed -E 's/^[^a-zA-Z]+//' | grep -vE "^($ALLOW)$" \
  && { echo "unknown Maestro command (above)"; exit 1; } || true

echo "OK: $FLOW"

It's a lint, not a full parse — Maestro stays the source of truth (layer 4). It just moves the cheapest mistakes off the device and onto a sub-second check, and would slot in as the gate run_flow.sh calls first.
